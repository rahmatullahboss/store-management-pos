# Store Companion — API and Contract Design

## 1. Contract principles

- Mobile consumes task-oriented, versioned APIs; it does not expose database-shaped CRUD.
- Every request is tenant-, actor-, workspace- and permission-scoped by the server.
- Retryable mutations require an idempotency key.
- Mutable workflows use optimistic concurrency/version preconditions.
- Exact money and quantities are serialized as decimal strings or scaled-integer strings with explicit metadata.
- Unknown additive enum values are tolerated by supported clients.
- Errors use stable codes, localized display messages and trace IDs without SQL, secrets or restricted payloads.
- Large exports, reports and uploads are asynchronous or direct-to-object-storage workflows.
- The mobile route family composes existing module contracts; it does not own their business state.

## 2. Versioning and headers

Suggested base path:

```text
/v1/mobile
```

Required request context:

```text
Authorization: Bearer <short-lived access token>
X-Workspace-Context: <server-issued opaque context reference>
X-Client-Version: <semantic version>
X-Client-Build: <integer/string build>
X-Device-Id: <registered opaque device reference>
X-Request-Id: <UUIDv7 where client-generated requests are supported>
Idempotency-Key: <required for retryable commands>
If-Match: <version/ETag for mutable resources where applicable>
Accept-Language: <BCP 47 preference list>
```

The server returns:

```text
X-Request-Id
X-Trace-Id
ETag where applicable
Cache-Control appropriate to classification
```

The client-provided workspace/device references are never trusted without matching verified session state.

### `POST /v1/mobile/workspaces/select`

Validates the selected workspace and returns refreshed bootstrap/capability context. It is not an authorization grant.

## 4. Device lifecycle

### `POST /v1/mobile/devices/enrol`

Inputs:

- one-time authenticated enrolment challenge;
- installation identifier generated by the app;
- platform, app version/build and supported capabilities;
- push-provider token separately or in a subsequent request;
- device attestation/risk evidence only where policy requires and privacy permits.

Outputs:

- opaque device ID;
- status;
- credential/session binding references;
- policy and expiry;
- no reusable server secret exposed to logs.

### `PUT /v1/mobile/devices/{device_id}/push-token`

Idempotently registers/rotates one provider token with environment, platform and app-build metadata. Old tokens are revoked when the provider reports invalidation or the device is removed.

### `POST /v1/mobile/devices/{device_id}/revoke`

Self-revocation or privileged server workflow. Revocation invalidates sessions and restricted cached data according to policy. Unsynchronised non-financial drafts receive an explicit recovery/export decision; revocation never silently submits them.

## 5. Change feed

### `GET /v1/mobile/changes?cursor=...&collections=...`

Returns permission-scoped incremental changes for approved collections.

Response:

```json
{
  "contract_version": "mobile-changes.v1",
  "from_cursor": "...",
  "next_cursor": "...",
  "has_more": false,
  "collections": {
    "catalog": {
      "projection_version": "...",
      "upserts": [],
      "deletions": []
    },
    "assigned_work": {
      "projection_version": "...",
      "upserts": [],
      "deletions": []
    }
  },
  "server_time": "..."
}
```

Rules:

- cursor is scoped to tenant/workspace/device and cannot be replayed across scopes;
- deletions are tombstones or archive transitions, not evidence that a restricted record exists;
- collection payloads are bounded and paginated;
- a cursor-expired result supplies a signed/versioned snapshot path;
- restricted data is removed or invalidated when capability/scope changes;
- stock values include freshness and are never treated as checkout authority.

### Snapshot bootstrap

Large projections use an R2 object with:

- signed short-lived URL;
- checksum;
- schema/projection version;
- high-water cursor;
- tenant/workspace binding;
- expiry and classification;
- compressed, bounded records.

The client verifies checksum/version before activation and atomically swaps projections while preserving pending operations.

## 6. Operation batch

### `POST /v1/mobile/operations:batch`

Request envelope:

```json
{
  "contract_version": "mobile-operation-batch.v1",
  "device_id": "opaque",
  "workspace_context": "opaque",
  "client_cursor": "...",
  "operations": [
    {
      "operation_id": "UUIDv7",
      "local_sequence": "1",
      "operation_type": "inventory.count.submit.v1",
      "schema_version": 1,
      "created_at_utc": "...",
      "created_at_local": "...+06:00",
      "business_date": "2026-07-29",
      "idempotency_key": "...",
      "base_version": "...",
      "payload_hash": "sha256:...",
      "dependencies": [],
      "payload": {}
    }
  ]
}
```

Response:

```json
{
  "contract_version": "mobile-operation-results.v1",
  "server_cursor": "...",
  "results": [
    {
      "operation_id": "...",
      "status": "accepted",
      "server_reference": "...",
      "server_version": "...",
      "error": null,
      "adjustments": [],
      "trace_id": "..."
    }
  ]
}
```

Statuses:

- `accepted`;
- `accepted_with_adjustment`;
- `duplicate_replay`;
- `deferred`;
- `requires_online_confirmation`;
- `requires_approval`;
- `conflict`;
- `rejected`;
- `superseded`;
- `unknown_external_state`.

One invalid operation does not erase independent later operations. Dependency-linked operations remain blocked until their prerequisites are accepted or explicitly superseded.

## 7. Operational queries and commands

The route names below are composition examples. Existing module routers remain authoritative and may be called directly by the generated client when their contracts already fit mobile needs.

### Catalog and stock

```text
GET /v1/mobile/catalog/lookup?barcode=...
GET /v1/mobile/catalog/items/{id}
GET /v1/mobile/inventory/balances?item_id=...&location_id=...
GET /v1/mobile/inventory/movements?item_id=...&cursor=...
```

Responses include scope, source version, as-of/freshness and bounded fields. They do not promise checkout availability.

### Receiving

```text
GET  /v1/mobile/procurement/purchase-orders?assigned=true&cursor=...
GET  /v1/mobile/procurement/purchase-orders/{id}/receiving-context
POST /v1/mobile/procurement/purchase-orders/{id}/receipts
```

The command delegates to the MOD-B receiving service and returns stock-posting/source references. It does not write stock balances directly.

### Counts and transfers

```text
GET  /v1/mobile/inventory/counts?assigned=true
POST /v1/mobile/inventory/counts/{id}/submit
POST /v1/mobile/inventory/transfers/{id}/dispatch
POST /v1/mobile/inventory/transfers/{id}/receive
```

All exact quantities, serial/batch uniqueness, variance approval and transfer state rules remain inside MOD-B.

### Customer, quotation and order

```text
GET  /v1/mobile/customers?query=...&cursor=...
POST /v1/mobile/customers
GET  /v1/mobile/sales/quotes?cursor=...
POST /v1/mobile/sales/quotes
POST /v1/mobile/sales/quotes/{id}/revisions
GET  /v1/mobile/sales/orders/{id}
GET  /v1/mobile/fulfilment/work?assigned=true&cursor=...
```

These delegate to MOD-C and preserve its immutable snapshots, credit checks, availability, return/refund provenance and permissions.

## 8. Unified approvals

### `GET /v1/mobile/approvals?cursor=...&status=pending`

Returns an authorised composition of approval references, not copied approval state.

Each item includes:

- approval ID/version;
- owning module;
- source type and opaque ID;
- requested action;
- risk/severity and expiry;
- exact amount/currency or quantity context where allowed;
- reason/evidence summary;
- required assurance;
- safe source-preview fields;
- supported decisions.

### `POST /v1/mobile/approvals/{id}/decisions`

Inputs:

- approval version/ETag;
- decision;
- reason;
- evidence references;
- assurance proof/reference;
- idempotency key.

The route calls the owning module's approval command. It cannot fabricate approval completion or bypass threshold rules.

## 9. Notifications and deep-link references

### `GET /v1/mobile/notifications?cursor=...`

Returns tenant-authorised notification references and current read/delivery state.

### `POST /v1/mobile/notifications/{id}/read`

Idempotently marks the user's notification reference read where the communications contract permits.

Push payloads contain minimal reference and type only. The current record is fetched after authentication.

## 10. Uploads and evidence

### `POST /v1/mobile/uploads/intents`

Creates a short-lived signed upload intent with:

- tenant/workspace and owner module;
- purpose and classification;
- allowed MIME signatures, size and count;
- immutable object key;
- checksum requirement;
- malware/processing status path;
- expiry.

The mobile app uploads directly to the approved private object endpoint, then confirms the reference through the owning domain command. Local staged files are deleted according to confirmed upload, retention and pending-operation state.

## 11. Reporting dependency

MOB-01 must not invent cross-module KPI formulas. After MOD-G publishes governed reporting contracts, mobile may consume:

```text
GET /v1/mobile/dashboards/{persona}
GET /v1/mobile/metrics/{metric_id}/drill?filters=...
POST /v1/mobile/reports/jobs
GET /v1/mobile/reports/jobs/{id}
```

Every metric response includes definition/version, period, timezone, currency, dimensions, freshness and reconciliation state.

## 12. Errors

Standard shape:

```json
{
  "error": {
    "code": "inventory.count.version_conflict",
    "message": "This count changed after your draft was loaded.",
    "details": {
      "safe_fields_only": true
    },
    "trace_id": "...",
    "retryable": false,
    "recovery": "refresh_and_reconcile"
  }
}
```

Client handling classes:

- authentication/session;
- authorization/restricted/masked;
- validation;
- optimistic conflict;
- approval/assurance required;
- offline/online-required;
- transient service/provider;
- unknown external state;
- minimum-client/API incompatibility;
- data removed/superseded;
- internal error with safe recovery.

The client preserves user drafts for recoverable errors and never displays stack traces or raw provider/database messages.

## 13. Compatibility tests

Required contract tests:

- bootstrap across multiple memberships/scopes;
- removed capability and tenant switch;
- unknown additive enum;
- old supported client against additive server response;
- minimum-version rejection;
- idempotent same-key/same-request replay;
- same-key/different-request rejection;
- ETag/version conflict;
- duplicate/out-of-order operation batch;
- partial batch results;
- cursor expiration and snapshot rebuild;
- restricted tombstone/no-existence leakage;
- device/session revocation;
- MOD-F effective configuration changes;
- MOD-G metric definition/freshness requirements;
- trace ID propagation and sensitive-field redaction.
